## ⚖️ RISK-TIERED REVIEW ROUTING (NEW in v4.4 — replaces "always 5-agent")

**Why:** running 5-agent review on every routine feature wasted ~15-20K tokens per feature without proportional benefit. We now match review depth to risk.

| Trigger | Review depth | Approx cost |
|---------|--------------|-------------|
| Routine feature (single module, no auth/$/PII) | **Inline review** (5-question checklist below, no extra LLM pass) | ~0 extra tokens |
| Complex feature (multi-module, non-sensitive) | **1-agent thorough review** (Sonnet) | ~5K |
| **Security-sensitive** — touches **auth, payments, PII, file uploads, RBAC, secrets, raw SQL, anything user-uploaded executed** | **`/code-review` 5-agent parallel** | ~20K |
| Pre-PR / pre-merge to main / milestone | **`/code-review` 5-agent parallel** | ~20K |
| Inline review surfaces unresolved Risk=HIGH item | **Escalate** → `playbooks/self-review-full.md` + `/code-review` | ~25K |

**Quality guard:** when in doubt about whether something is "security-sensitive," treat it as YES and escalate. Cheaper review is opt-down, not opt-out.

## 🔍 INLINE SELF-REVIEW (NEW — runs DURING implementation, not as a second pass)

After completing any task, before claiming "done," answer these 5 questions IN-PLACE. This costs no extra LLM round-trip — it's part of the implementation prompt to yourself.

```
INLINE REVIEW: T-XXX
1. ⛓️ Chain complete? DB → API → UI all wired with REAL data, no mocks?
   → If NO → fix now.
2. 🔒 Security clean? Inputs validated server-side, no raw SQL, auth checked, no secrets in code?
   → If NO → fix now. If touched auth/$/PII → ESCALATE to /code-review.
3. 🧪 Tested for real? At least: 1 happy path + 1 validation error + 1 auth/edge case, all assert SPECIFIC values?
   → If NO → write missing tests now.
4. 🎨 Design honest? (frontend only) Colors/spacing/typography from DESIGN.md only? Loading + empty + error + success states present?
   → If NO → fix now.
5. 🚨 Risk = HIGH on anything? (data loss path, irreversible action, unbounded loop, external write, performance regression on hot path?)
   → If YES → ESCALATE to `playbooks/self-review-full.md` + run /code-review.
```

Print one of these as your task footer:

```
🔍 INLINE REVIEW: PASS  (chain ✅ | security ✅ | tests ✅ | design ✅ | risk LOW)
```
or
```
🔍 INLINE REVIEW: ESCALATED  (reason: [security-sensitive | risk HIGH | pre-PR])
   → docs/reviews/review-T-XXX.md created
```

**Quality guarantee:** the inline review covers the same ground as the v4.3 7-category check; the FULL fallback (`playbooks/self-review-full.md`) is still available when escalated. By embedding the checklist in the implementation prompt instead of running a separate LLM pass, we save **~2-4K tokens per routine task** (the inline checklist itself costs ~500-800 output tokens — real savings are net of that, not gross).

## 🎯 DEEP FOCUS MODE (the most important behavioral rule)

When given a plan with 10 tasks, the temptation is to do all 10 at once → skips details → produces shallow work.
When given 1 task at a time, you go deep → creative → high quality.

### The Rule: SINGLE TASK DEEP EXECUTION

```
⛔ NEVER DO THIS:
  "Let me implement tasks T-001 through T-005..."
  "I'll set up the database, create the API, and build the frontend..."
  "Let me quickly scaffold all the modules..."

✅ ALWAYS DO THIS:
  "Working on T-001: Create users table migration."
  [Complete T-001 fully with maximum depth]
  [Inline self-review T-001]
  [Update tracking docs]
  "T-001 complete. Moving to T-002: Create User entity."
```

### Deep Execution Checklist (apply to EVERY task):
```
Before starting:
  □ What EXACTLY am I building? (specific, not vague)
  □ What are ALL the edge cases?
  □ What validation is needed?
  □ What error handling is needed?
  □ What are the security implications?
  □ How does this connect to existing code?

During implementation:
  □ Am I taking shortcuts? → STOP, do it properly
  □ Am I skipping validation? → STOP, add it
  □ Am I leaving TODOs? → STOP, implement now (unless blocked by dependency)
  □ Am I copy-pasting without understanding? → STOP, write it fresh
  □ Am I rushing to finish? → STOP, quality over speed

After completing:
  □ Would a senior engineer approve this code?
  □ Is every function/method complete, not stubbed?
  □ Are all edge cases handled?
  □ Is error handling comprehensive?
```

### Plan Mode Behavior:
When asked to make a plan for multiple tasks:
1. YES — create the plan showing all tasks.
2. NO — do NOT start implementing multiple tasks from the plan.
3. After plan is created, say: "Plan created with [N] tasks. I'll implement them ONE AT A TIME with full depth. Starting with T-001: [description]."
4. Implement ONLY T-001 with maximum depth.
5. Complete T-001 → inline self-review → then proceed to T-002.

## 🏗️ DEVELOPMENT RULES (NON-NEGOTIABLE — do not compress)

### Rule 1: Sequential Task Execution
ONE task at a time. Complete fully before starting next. "Fully complete" means ALL of:
- [ ] Code written and compiles without errors
- [ ] Connected to real API (if frontend) or real DB (if backend)
- [ ] At least happy path + one validation test passing
- [ ] **Feature progress updated** — `FEATURES.md` row (Full tier) **OR** `SESSION.md` → Feature Tracker row (Lite/Standard tier)
- [ ] TASKS.md checkbox marked [x] (Full tier; Lite/Standard tracks tasks inline in SESSION.md)
- [ ] SESSION.md current state updated

### Rule 2: ZERO Mock/Static Data in Production Code
```
⛔ FORBIDDEN:
  const users = [{ name: "John", email: "john@test.com" }]   // hardcoded
  return res.json({ data: "placeholder" })                    // fake response
  <Card title="Sample Product" price="$99" />                 // static props

✅ REQUIRED:
  const { data: users } = await api.get('/users')             // real API call
  return res.json({ data: await userService.findAll() })       // real DB query
  <Card title={product.name} price={product.price} />          // real props from API

🟡 EXCEPTION — only in:
  seed/            → test fixture data
  tests/fixtures/  → test data
  .env.example     → placeholder config
  Storybook files  → component dev only
```

### Rule 3: Complete Connection Chain
Every feature MUST have this full chain verified:
```
DB Table → Entity → Repository → Service → Controller → Route → Frontend Component → User sees REAL data
```
If ANY link is missing → feature status = ❌ NOT DONE.

### Rule 4: Error Handling Everywhere
**Backend (every endpoint):** 400, 401, 403, 404, 409, 422 (with field-specific errors), 429, 500 (logged, generic message to client).
**Frontend (every data component):** Loading, Empty, Error, Success, Offline (if applicable).

### Rule 5: Security by Default (apply to EVERY endpoint and form)
- Server-side input validation (never trust frontend)
- Parameterized queries — NEVER concatenate user input into SQL
- Password: bcrypt, minimum 12 rounds
- JWT: short access (15min), refresh (7d), httpOnly cookies if possible
- CORS: whitelist origins, not "*" in production
- Rate limit: auth endpoints (5/min), general API (100/min)
- File uploads: validate type, limit size, sanitize filename
- Output encoding: escape HTML in user-generated content
- Helmet.js / security headers: always enabled

### Rule 6: Type Safety (TypeScript)
- `strict: true` — no exceptions
- No `any` (use `unknown` + type guard)
- DTOs with class-validator on ALL API inputs
- Interface/Type for ALL API responses
- Enum for fixed value sets
- No `@ts-ignore` — fix the type
